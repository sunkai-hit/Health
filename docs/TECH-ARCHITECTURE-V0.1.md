# Health V0.1 技术架构方案（研发评审稿）

- 日期：2026-11-17
- 状态：设计方案，**不是已部署系统**
- 范围：个人健康事件、人体位置、用药、就医、医嘱/处方、治疗、报告、AI 辅助
- 决策约束：部署区域、首批用户、账号体系、AI/医疗监管尚未全部确认；禁止使用真实健康数据做未审查的工程试验

## 1. 结论与架构原则

**推荐：移动优先 PWA + TypeScript API + SQLite 兼容关系数据库 + 私有对象存储 + 异步文档/AI 适配层。**

1. 核心“健康事件”记录独立于 AI：模型故障不阻塞保存、查询、时间线与就医报告。
2. 业务事实分离：医生医嘱/处方、实际用药、实际治疗、实际就诊分别存储，不以某个状态自动生成另一个事实。
3. 数据存储与第三方模型可替换：通过接口适配器选择 Workers/D1/R2 或其他满足数据所在地要求的服务。
4. 默认最小化敏感数据；用户身份校验发生在服务端，不相信客户端传来的 owner_id。
5. 结构化数据保留来源、精度、版本及用户更正历史；已导出的报告保留生成快照，之后的改动不能无声更改历史。
6. **医学分诊和自动风险等级**必须通过医学及适用监管评审才可能在生产环境开启；纯记录/事实摘要可以独立交付。
7. 原型与真实开发环境彻底隔离；仓库仅允许虚构/合成测试数据。

### 2.1 前端

- 方案：TypeScript、React/Vue 等组件化 PWA（框架待定）；人体图保留 SVG + 区域/层级编码，可用纯文本列表选择作无障碍替代。
- 应用导航：健康首页、症状记录、事件时间线、用药、就医及医嘱、AI 辅助、报告、个人档案与隐私。
- 表单：草稿明确保存状态，输入最小化；用户确认后写入服务端；时间使用 UTC 存储、界面显示用户选定时区。
- **禁止把原始健康数据放到 LocalStorage**；如以后确需离线加密存储，单独设计授权/设备密钥、锁屏、失窃和数据清理策略，首发暂不启用。
- 对于急症提醒，未来独立的已审核规则在前端有高优先级呈现，不依赖 AI 文案。
- 不在第三方统计 SDK、错误日志、URL 查询参数或浏览器历史中泄露症状/药名/病历全文。

### 2.2 核心后端

- 建议按领域拆分模块，V0.1 可保留单一部署的模块化单体，以减少研发和运维复杂性。
- \`identity\` / \`consent\`：会话、权限、同意、撤回、数据导出/删除。
- \`health-events\`：健康事件、症状条目、身体部位标记、来源、修订。
- \`medication\`：实际用药记录、与处方条目的可选关系。
- \`care\`：就诊、医嘱、处方药品项、治疗执行、复诊计划与实际复诊引用。
- \`reports\`：就医前摘要、全程档案、用户确认、可下载报告快照。
- \`attachments\`：私有文件、扫描/大小/MIME 校验、原文处理权限。
- \`ai-gateway\`：基于同意的最小数据选择、请求校验、供应商适配、失败/取消。
- \`risk-rules\`：独立于模型、版本化、医学审查/测试；直到符合发布门槛一直关闭临床分诊输出。

### 2.3 数据层

- 关系数据库：优先 SQLite 兼容结构，开发时可用本地 SQLite；生产按部署地区选择 D1 或 PostgreSQL 等适配层。
- 附件对象存储：存储密钥随机化，不直接公开；健康相关图片、处方、报告需强制所有权校验、下载签名短期有效，并按授权/地域设计。
- 敏感数据可采用字段/载荷层的应用加密（如 envelope encryption），主密钥不入 Git、不在前端，解密必须由经过权限校验的服务进行；具体 KMS/密钥轮换由安全设计定稿。
- 数据库仅保留最少可索引元信息；症状文本、医嘱及药物明细等敏感内容应进入加密载荷。详见 \`db/migrations/0001_initial.sql\`。
- 数据库灾备、备份删除及保留策略需与敏感数据合规方案一致，不以简单软删替代永久删除请求。

## 3. 部署候选方案（**尚未选定**）

### 3.1 方案 A：Cloudflare（适用地区经过确认后）

- Pages / Workers 负责前端和 API；D1 存储结构化记录；R2 作为私有附件对象存储；密钥使用 Workers Secrets / 合法可用的外部 KMS。
- 资源通过环境绑定访问，不在前端暴露账号、API Key、数据库连接字符串。
- 开发环境只接受合成测试资料；正式用户资料应先通过数据驻留、跨境、第三方模型及日志服务审查。
- D1 的具体数据驻留辖区目前为 **US/EU/FedRAMP**，apac 只是位置提示、不保证中国大陆境内。
- R2 的明确辖区同样包括 **US/EU/FedRAMP**，位置提示不能代替合规的数据驻留保证。
- 如首批用户在中国大陆，本方案**暂不得被默认为符合中国大陆数据本地化要求**；应优先评估适当的数据境内托管和合法的数据传输/处理方案。

### 3.2 方案 B：地区合规云 + 同样 API/业务模型

- 选择能满足目标用户所在地区数据处理和部署要求的云服务；Web API、结构化 DB、私有对象存储、KMS、异步任务队列都通过适配层实现。
- 支持先在本地 SQLite + 私有测试对象存储完成业务闭环，再迁移到实际生产数据库。
- 不依赖 Cloudflare 的不可移植 SQL、队列或认证特色作为业务核心；用适配接口隔离。

### 3.3 当前建议

**需求和原型继续使用独立模拟环境；正式数据部署决策保持开放。** 不提前创建真实生产数据库、对象存储桶、AI 密钥或自动化导入流程。

## 4. 关键数据边界

### 4.1 医嘱与执行

\`\`\`mermaid
erDiagram
    PROFILE ||--o{ HEALTH_EVENT : owns
    HEALTH_EVENT ||--o{ EVENT_ENTRY : logs
    HEALTH_EVENT ||--o{ ENCOUNTER : has
    ENCOUNTER ||--o{ CLINICIAN_ORDER : related
    HEALTH_EVENT ||--o{ CLINICIAN_ORDER : records
    CLINICIAN_ORDER ||--o{ PRESCRIPTION_ITEM : contains
    CLINICIAN_ORDER ||--o{ ACTUAL_MEDICATION : referenced_by
    PRESCRIPTION_ITEM ||--o{ ACTUAL_MEDICATION : item_reference
    CLINICIAN_ORDER ||--o{ TREATMENT_PERFORMED : referenced_by
    CLINICIAN_ORDER ||--o{ ENCOUNTER : followup_reference
\`\`\`

- 原始医生医嘱与用户转录来源一并保留；药物处方和实际服药是不同表。
- \`order.supersedes_order_id\` 记录新旧版本，不覆盖旧医嘱。
- 计划复诊可关联真实就诊，但不能单凭计划判定已复诊。
- 各健康事件和附件的用户归属都要服务端校验；外键不代替权限校验。

### 4.2 人体标记与时间

- 采用 \`map_version\`、\`zone_code\` 和左右侧、正背面，不依赖用户点击坐标做医学结论。
- 记录发生时间和录入时间独立，允许时间精度为“不确定”，不强行补为当前时间。
- 用户自述、文书转录、OCR 草稿、机构核验和 AI 生成必须明确区分；不能由模型直接提升资料可信等级。

## 5. 典型业务链路

### 5.1 新增症状

PWA 输入 → 会话校验 → 授权服务 → 后端字段校验 → 事件归属校验 → 事务写入条目/部位 → 返回条目 ID/版本 → 前端更新事件时间线。AI 可以作为另外的可选请求，与保存解耦。

### 5.2 新增处方与实际用药

医生处方转录 → 新医嘱（可选 \`supersedes\`）→ 逐药处方条目 → **用户手动创建实际服药记录** → 可选关联旧/新处方的某药品。服务端验证关联对象属于同一用户和事件；禁止写入自动推导的“已服药”事实。

### 5.3 附件/OCR（以后）

用户主动上传 → 文件大小/类型检查、授权/扫描 → 私有附件存储 → OCR 候选草稿 → 用户逐字段核对 → 创建结构化记录；附件和 OCR 结果具备来源记录。当前原型**只进行本地图片预览**，无任何真正的 OCR。

### 5.4 报告

选择事件及模式 → API 查询已授权记录 → 脱敏/筛选 → 草稿预览 → 用户确认 → 生成不可变快照 → 私有下载。AI 推断与原始事实独立分区，默认不附加模型解释。

## 6. 质量和工程非功能要求

- 安全：TLS、服务端归属校验、限流、输出转义、CSRF（若采用 Cookie 会话）、凭据轮换、依赖审计、文件上传扫描与沙箱处理。
- 隐私：最小化授权、目的说明、独立 AI 同意、可撤回、导出、删除、跨境审查、审计日志避免正文。
- 可靠性：数据库迁移可重放、备份恢复演练、AI 故障时核心功能可用。
- 可观测：记录延迟/错误计数、审计 ID、接口版本；**不记录症状、药品、医疗图像、AI 提示全文到普通错误日志**。
- 性能目标（待真实压测确认）：移动端普通症状录入以简洁、快速为优先；报告复杂分页另行验证。
- 测试：纯函数/SQL 迁移测试 → API 所有权及脱敏测试 → 浏览器 E2E → 移动端走查 → 真实医学风险功能独立安全验收。

## 8. 阶段门

G1 产品边界确认：首批使用地区/人群、家庭档案是否首发、正式 P0/P1。
G2 数据安全：身份认证、授权、存储区域、AI 同意、附件和删除方案审核。
G3 功能验收：医生医嘱与实际执行分离、报告事实来源清晰、全流程 E2E。
G4 医学/监管（仅自动医疗风险判断）：规则审查、验证集、异常处理、适用监管判断。

没有跨过 G2 不得接入真实健康数据；没有跨过 G4 不得启用真实自动风险分级。
