# 医嘱、治疗与实际用药管理需求 V0.1（2026-11-17 迭代评审稿）

> 归属：Health V0.1；需求增补，非独立医疗系统。已获产品方向认可，但字段和发布范围仍按评审执行。  
> **原则：医生开具/建议 ≠ 患者已执行；用药处方 ≠ 实际服药；计划治疗 ≠ 实际治疗。**

## 1. 增补背景与目标

原方案覆盖“症状 → 服药 → 就医摘要”。真实健康事件就医后仍会继续：医生给出诊断意见、开具处方、安排检查/复诊/治疗，用户回家继续服药、接受治疗并观察身体变化。

因此产品从单纯的**就医前资料整理**扩展到**就医前准备 + 就医后医嘱记录 + 治疗和用药执行留痕 + 下次复诊信息回顾**的连续闭环。医生是报告的阅读者，但在首版并非系统账号用户；录入的“医生医嘱/意见”主要来自用户的记录和转录，不能展示为已由医生实名认证或系统核验。

## 2. 业务角色与边界

- **记录人**：本人，选择事件、补充就医记录、录入所获医嘱、确认实际执行、控制分享。
- **医疗人员**：在真实生活中提供医嘱或实施治疗；V0.1 不向医生开放在线开医嘱、审批、处方签名等业务。
- **AI**：可以在明确授权下将医嘱图像文字识别为**待确认草稿**，协助分类与摘要；不得修改原意、擅自补充剂量、转成医嘱、代替医生作出医疗决定。
- **系统**：维持来源、时间、关联关系与修订痕迹；不自动判断医嘱是否医学正确，也不自动判断依从性或治疗有效性。

## 3. 业务实体与分离原则

### 3.1 就诊 Encounter（一次看诊）

用于记录就诊时间、医院、科室、医生（可选）、医生口头说明（用户转录）及来源材料。一个健康事件可以关联多次就诊；就诊产生多条医嘱，并可能对应检查/诊断，但不能把“医生建议做某检查”自动认定成“检查已完成”。

**最小字段**：
- encounter_id / health_event_id
- visited_at（实际就诊时间）、facility_name、department、practitioner_name（可选）
- complaint_summary / diagnosis_reported / notes_original（按需要）
- source_type（self_report / document_transcribed / verified_import）
- source_attachment_ids / confirmed_by_user / recorded_at / revised_at

### 3.2 医嘱/处方 ClinicianInstruction（医生提出的要求）

一条医嘱必须关联健康事件，可选关联就诊记录；将医嘱分为：
- 药物处方（药名、规格、剂型、一次用量、频率、疗程、服用途径等字段均可**未知**；不得擅自补齐）
- 治疗/处置建议（治疗项目、预期次数、时间安排）
- 检查检验安排（建议检查，不等于已经完成）
- 复诊/复查安排（到期时间可明确或仅文本）
- 生活方式及注意事项
- 其他原文

**必须保存原文与来源**：人工记录、用户口述、转录的纸质/电子处方、后续可能的合法医疗机构数据源。对用户回忆输入标示“待核实”，对照片 OCR 标示“识别草稿”，对正式文书按实际来源显示，不应默认为医生在本系统签署。

**医嘱状态**与执行记录分离：
- unknown：执行情况不明确
- not_started：尚未开始/未执行
- in_progress：执行中（用户标记）
- reported_completed：用户表示已完成（仍需要执行事实记录支持）

禁止仅通过修改状态就自动生成用药或治疗事实。

### 3.3 实际治疗 TreatmentPerformed（执行事实）

不同于“治疗建议”，记录何时真正进行了什么治疗/处置：名称、时间、地点/机构（可选）、实施次数、患者反应、来源、关联的医嘱（可选）。同一治疗建议可对应多个执行条目。

示例：11月18日医生建议进行某治疗；11月20日第一次实际实施；11月22日第二次实际实施——这是**一条医嘱，两条实际治疗记录**，不能合并成一次已完成。

### 3.4 实际用药 MedicationUse（已有对象扩展）

实际服药属于已发生事件：药名、剂型与规格（如有）、剂量值与单位、时间、是否真正服用、患者主观反应、来源。可通过 \`instruction_id\` 或更精细的 \`prescription_item_id\` 指向对应处方。

重要判定：
- 处方写“每日两次”不意味着患者已经服用了两次。
- 患者实际服用的剂量与医嘱可能不一致；**并列记录原始差异**，不得自动把实际情况改为医嘱，也不能直接给出改药建议。
- 无对应处方时允许录入实际用药（例如 OTC 或自行记录），仅记录事实，不评价其合理性。
- 模糊药名、无法辨识规格、单位缺失要保留未知，不能自动换算或猜测。
- 处方 OCR/药盒 OCR 只能生成待用户确认草稿。

### 3.5 后续情况 / 观察记录

每次治疗或用药后，用户可以新增主观变化记录（改善、无变化、加重、不明确），在时间线上与相关治疗条目建立引用，但不把时间相关性直接判定为因果。

## 4. 业务流程（推荐）

\`\`\`mermaid
flowchart TD
    A[健康事件：不舒服] --> B[症状记录及就医前摘要]
    B --> C[一次就医 Encounter]
    C --> D[记录医生意见及医嘱原文]
    D --> E{医嘱类型}
    E -->|药物| F[处方记录]
    E -->|治疗| G[治疗建议]
    E -->|检查或复诊| H[检查和复诊安排]
    F --> I[实际服药 MedicationUse]
    G --> J[实际治疗 TreatmentPerformed]
    H --> K[完成检查或再次就诊的独立记录]
    I --> L[症状和后续变化]
    J --> L
    K --> L
    L --> M[全程健康事件档案 / 复诊报告]
\`\`\`

### 4.1 记录就医

从事件详情点击“就医/医嘱/治疗” → 选择健康事件 → 录入就诊时间、医疗机构、科室、医生意见（自述或文书） → 保存就诊条目。允许机构、科室等未知。不能将用户自行填写的诊断归类为系统核实的医学诊断。

### 4.2 记录医嘱

选择事件 → 可选关联某次就诊 → 医嘱类型 → 原文/字段 → 原文来源 → 状态 → 保存。一个就诊可以拥有多条医嘱。处方涉及药名规格剂量时，每条细分药物应有独立明细及核对状态；原型阶段暂以完整文字记录来验证流程。

### 4.3 记录实际用药和治疗

选择事件 → 录入实际发生的行为及时间 → 可选关联处方/治疗医嘱 → 保存独立执行条目。系统不依据医嘱自动生成实际执行记录。已结束的事件仍允许补记历史行为并标记发生时间与录入时间差异。

### 4.4 下次复诊

按事件/日期范围生成全程报告：呈现首次症状、用药、就诊、医嘱、实际治疗与变化，同时提示哪些条目是用户自述，哪些有原始文书佐证。医生可据此核对治疗历史，产品不会以“已执行”状态替代医疗事实。

## 5. 两种报告视图

### 5.1 就医前摘要（默认）

- 主诉与症状时间线、人体部位示意
- 近期**实际**用药（非所有处方）
- 重要已知病史/过敏（正式版、按用户选择展示）
- 需要向医生核对的问题
- 原始记录来源与生成时间

不把拟开医嘱和已发生用药混写；默认不附 AI 疾病猜测。

### 5.2 就医及治疗全程档案（新）

在就医前摘要的基础上增加独立分区：
- **实际就诊记录**：医疗机构、科室、就诊时间、医生说明（标注来源）
- **医生医嘱/处方**：开具时间、原文、类型、来源、用户标记的执行状态
- **实际用药记录**：每次真正服用的药物、数量、时间，与处方的可选关联
- **实际治疗/处置记录**：项目、实施时间、次数、患者自述感受，与医嘱的可选关联
- **检查/复诊后续**：建议与实际完成记录分离；首版完整检查表单仍需进一步细化
- **症状变化与复诊待问问题**：用户自述时间线

**报告默认显示信息来源和事实性质**。实际执行信息不能仅根据医嘱状态推断。用户可选择隐藏敏感项；未来正式版需要具备报告快照与修订追溯。

### 5.3 医嘱差异及版本

若医生新开医嘱改变旧处方，保留两条原始医嘱、日期及失效/替代关系，不允许直接覆盖旧记录而失去历史。后续需要研究“医嘱被撤销/更改”“患者停止某药”和“患者没有记录该药”的区别。

## 7. 来源与可信度

| 来源类别 | 对用户展示 | 可自动充当医生确认证据？ |
|---|---|---|
| 用户回忆/口述 | “用户自述 / 待核实” | 否 |
| 用户手录纸质处方 | “根据文书转录 / 原件未核验” | 否 |
| OCR 图片提取 | “识别草稿 / 待用户确认” | 否 |
| 合法渠道获得的可核验电子病历 | “由医疗机构提供（已核验来源）” | 仅在真正完成来源核验后 |

所有医嘱原文可改动时应保留修订历史和来源，不得由 AI 自动改写且覆写原文。

## 8. 验收例子

1. 单个事件有两次门诊记录，两次各关联医嘱，时间线按发生时间排序。
2. 一条处方建议每日用药，若用户没有实际用药记录，则报告不能显示“已按医嘱服用”。
3. 用户录入实际用药后，可选择关联已有处方；报告分别展示“处方内容”和“实际服用”，保留各自时间。
4. 用户录入治疗建议但未做治疗，治疗执行栏应为空；医嘱状态是用户主观标记，不视为已实施。
5. 同一治疗建议关联两次治疗记录，两次时间独立展示。
6. 医嘱来源为自述时，报告显示待核实，不显示“已由医生确认”。
7. 就医前摘要与全程档案可切换，后者增加医生医嘱、治疗及就诊专区。
8. 用户未选择 AI 附录时，报告中不出现 AI 对疾病的判断。
9. 任何字段未填或未知，都不允许模型推测药量、频次和治疗结果。
10. 医嘱或治疗数据不得被提交到公开 GitHub、普通日志或未经授权的第三方服务。

## 9. 原型实现与正式版差异

本轮 \`prototype/v0.1\` 实现可输入三类数据、关联健康事件、医嘱与实际用药/治疗可选关联、报告双视图；**演示数据仅在页面内存**。

仍需后续实现：多药处方明细、原件附件、OCR、医嘱修改/撤销版本、账号和数据隔离、检查结果结构化、复诊提醒、审核流程及正式 PDF 快照。上述内容不能因原型中有表单就被认为已交付生产能力。

## 10. 标准概念参考
