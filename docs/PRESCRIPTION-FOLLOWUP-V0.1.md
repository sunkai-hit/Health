# Health｜处方结构化、医嘱变更与复诊管理 V0.1（需求深化）

- 形成日期：2026-11-17
- 状态：需求与交互评审稿；不具备可供真实患者使用的医疗核验/医学决策能力
- 产品主线：健康事件 → 就诊 → 医嘱/处方 → 实际执行 → 后续观察 → 复诊 → 全程报告
- 关联文档：\`PRD-V0.1.md\`、\`CARE-AND-ORDERS-V0.1.md\`、\`DATA-MODEL-V0.1.md\`

## 一、设计约束与优先级

本轮将上一版 P1 的“多药处方、医嘱版本、拍照入口”等内容提前**做原型验证**，但**不代表自动提升到正式产品首发 P0**。对真实医疗数据提供任何 OCR、AI 解释、分诊、药物风险判断前，须另行完成供应商、医学与隐私审查。

唯一可靠的事实边界：
1. **医嘱/处方是医生建议或请求的记录**，不是患者已经执行的事实。
2. **实际服药和实际治疗是用户录入的执行条目**，与医嘱关联只证明“用户将其关联”，不自动证明符合医嘱、疗效或依从性。
3. **医生医嘱的文字来源必须明确**：用户回忆、根据医嘱原件转录、OCR 待确认、经合法核验的机构来源（后续）。
4. **旧医嘱保留，不覆盖**。修改、撤销、停止、替代有不同业务语义，不能合并为“最新状态”。
5. **复诊日期是计划**，没有关联实际就诊记录不等于未就诊，关联就诊也不自动代表按时、完成所有医疗要求。

## 二、多药处方结构化设计

### 2.1 处方与药品明细

PrescriptionInstruction（归属某健康事件、可选关联一次就诊） → 0..N PrescriptionItem（每个药物单独一行）。录入最基本的医嘱原文，鼓励逐药录入可辨识信息。

每条药品明细建议字段：

| 分类 | 字段 | 说明 |
|---|---|---|
| 身份 | prescription_item_id, instruction_id | 不可变稳定 ID |
| 药品 | name_original / normalized_name? | 原始药名与可选标准名称分开 |
| 制剂 | strength_original / form_original | 剂型规格须有出处，不自动猜测 |
| 剂量 | dose_original / route_original | 保留医嘱原文，数字与单位可进一步结构化 |
| 频率 | frequency_original | 支持含糊表达，不能擅自转化固定计划 |
| 疗程 | duration_original / start/end_original | 不知道时留空 |
| 溯源 | transcription_source, confirmed_by_user | OCR 不得默认为确认 |
| 变更 | instruction_version / supersedes | 继承处方级别的版本来源 |

**验收：** 一张处方包含 2–5 种药物时，各药分别显示；一个药品缺少规格或疗程仍可保存，显示“未记录”，不凭模型补全。用户可删除误加的草稿明细；正式记录删除需要审计版本。

### 2.2 拍照录入（原型 / 后续生产）

1. 用户主动选择“拍照 / 相册 / PDF”，显示本地预览；不自动视为处方已核验。
2. **当前原型仅展示本地图片和文件名**，无实际 OCR、无服务端上传、无附件持久化；刷新页面图片消失。
3. 后续正式版：文件取得合法授权 → 执行 OCR → 生成原文与结构化候选项 → 逐字段标识识别置信度或“待人工确认” → 用户逐项核对 → 保存版本和来源。
4. 药名/用量/剂型/频次/疗程属于高影响字段，无法识别时不可填默认值或生成医生未写的内容。
5. 图片处理需要隐私授权、存储加密、删除与到期清理；不得把真实处方/病历提交公开代码仓库或普通日志。

## 三、医嘱版本和变更管理

- \`supersedes_instruction_id\`：新医嘱与被替代旧医嘱的关系；每次变更产生新版本且保留旧版原文。
- \`change_reason_original\`：医生变更/患者理解/更正录入？正式版应分别标识。
- \`revision_time\`、\`source_document\`、\`confirmed_state\`：区分医生正式调整与用户自行修订文本。
- \`status\`：active / superseded / canceled / unknown；**不能由用户凭空断定医嘱医学有效性**，仅按来源记录状态。

例：用户11月15日上传一份处方；11月17日新处方替换原处方。系统应在时间线上保留两次，并明确显示新旧关系。实际服药依然指向对应的原始处方版本及药品项，不应因替代而被错误改连。

**原型局限：** 只提供“新医嘱替代旧医嘱”的关联，没有真正验证医生修改/撤销事实，也未做删除/编辑审计。

## 四、医嘱与执行对照

建议分两个区域：

- 医嘱区：处方具体药物、频次及疗程原文、来源、日期、版本。
- 执行区：用户**主动记录**的实际用药条目（含时间、服用量、原始记录），治疗执行条目、复诊实际就诊条目。

用户可把每次实际用药关联到 \`instruction_id\` 和可选的 \`prescription_item_id\`。如果处方含多个药物，界面选择具体药品项可以降低歧义；不确定时允许只关联整张处方。

**仅做记录数量统计**（比如“对应药品已关联2条实际用药记录”），不要自动展示“服药完成率”“依从性百分比”“超量/漏服”“是否按医嘱治疗”等医学判断，因为频次、疗程、时间、用量可能不完整或不可信。

对照示例：

| 医嘱/处方 | 已关联执行信息 | 系统表达 |
|---|---|---|
| 处方 A，药品甲 | 2 条真实手工记录 | “已关联实际用药记录2条” |
| 处方 A，药品乙 | 无记录 | “没有关联记录，不代表未服用” |
| 治疗建议 B | 1 条执行记录 | “已记录实际治疗1次” |
| 复诊建议 C | 没有实际就诊关联 | “未关联就诊；不代表未复诊” |

## 五、复诊/复查安排

### 5.1 复诊计划

一条 \`followup\` 类型医嘱包含建议日期（可空）、就诊目的原文、来源及所属健康事件；可选与某次就诊关联。日期由用户转录，不做系统推算。

### 5.2 复诊实际发生

新建 Encounter 后，允许关联某条复诊计划。记录真正就诊的时间、医院、医生意见和后续医嘱。只通过用户明确录入的 Encounter 建立“有实际就诊记录”事实。

### 5.3 提醒（后续）

尚未安排自动提醒。未来明确提醒开关、时区、推送渠道、提前天数、用户可取消及敏感内容显示策略后才能实现。禁止根据原型状态擅自发送医疗建议或诊断提醒。

## 六、就医报告与版本快照

原有两种视图保留：
- **就医前摘要**：症状、时间线、定位、近期实际服药（事实来源）。
- **就医与治疗全程档案**：在上述基础上新增就诊记录、逐药处方、医嘱历史、实际用药/治疗关联、复诊计划与实际就诊对照。

完整报告的每一条医嘱必须显示来源级别；药物明细逐药列出规格/单次用量/频次/疗程（如未录入显示“不明”），不得根据 AI 猜测。

导出后应形成不可变报告快照，包括：\`event_snapshot_id\`、\`generation_time\`、\`included_entry_ids\`、\`report_mode\` 和用户核对状态。原型目前仅浏览器打印/保存 PDF，正式快照暂未实现。

## 八、验收场景

1. 多药处方：录入虚构药品甲/乙，规格为空不补全；保存后在事件/报告中出现两项。
2. 部分执行：实际用药只关联甲，乙呈现“无关联记录”，不能判定未服用。
3. 整方关联：不确定哪项药时允许只关联处方，且不自动计入每种药品的使用次数。
4. 新旧医嘱：新处方替代旧处方，旧处方保留；历史服药仍关联旧版。
5. 复诊安排：保存有日期的复诊医嘱，用户未录入实际就诊，则不出现“已完成”结论。
6. 复诊登记：新建就诊并关联复诊医嘱，全程报告同时呈现计划与实际时间。
7. 图片/文件：选择本地虚构处方图片可以预览；无法OCR，不上传，不保存原件。
8. 安全：特殊字符只当文本展示；刷新后所有新增记录与图片都不被持久化。
9. 同一事件可有多个处方版本、治疗记录和实际服药记录，彼此关系无串联错误。
10. 出现信息缺失时明确显示未知，不冒称医嘱已核验、治疗已完成、药量已核实。

## 九、生产功能未完成项

- 原始处方/电子文书上传及持久化、OCR 服务、识别置信度和逐字段人工核对；
- 药品标准字典及重复药名消歧、剂量单位规范；
- 医嘱签署/来源核验、撤销/停用和版本权限；
- 账号、隐私同意、存储加密、跨用户隔离、审计日志；
- 正式复诊提醒与用户通知渠道；
- 临床审核的用药风险策略及法规验证（不应因本功能设计自动启用）；
- 真机、浏览器端到端、隐私和医疗风险验证。

这些功能应先拆分评估，不能以原型展示即视为可上线。
