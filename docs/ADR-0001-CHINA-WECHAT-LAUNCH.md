# ADR-0001｜中国大陆首发与微信小程序架构决策

日期：2026-11-17
状态：**已确认的产品约束；具体云厂商和小程序主体尚待确认**

## 1. 已确认决策

- 首批用户：**中国大陆用户**（境外访问与跨境数据不作为首发目标）
- 用户端：**微信原生小程序（WXML/WXSS/JS）**，不以 PWA 或微信 WebView 作为首发主界面
- 服务端：适合中国大陆部署和访问的 API、关系型数据库、私有附件存储、KMS/加密服务；**具体云商待选**
- 首发登录：建议以微信小程序身份（\`wx.login → 服务端 code2Session → Health 自有短期会话\`）作为默认路径；**不强制用户提供手机号**，后续如有明确业务需求再单独授权绑定
- 核心业务范围不变：个人健康事件 → 症状及人体部位 → 时间线，后续迭代医嘱/处方/实际用药/就医报告；**绝不因此提前开发 AI 诊断或分诊**

## 2. 对此前技术方案的修订

| 既有技术方向 | 首发调整 | 处理方式 |
|---|---|---|
| PWA / React/Vue 移动前端 | 微信原生小程序 | 既有 \`prototype/v0.1\` 保留作体验/业务规则参考；不能直接当作微信原生代码运行 |
| 通用 OIDC + BFF 认证契约 | 微信 \`wx.login\` / code2Session 接入优先 | S3 OIDC 契约保留作未来其他平台的备选方案，**不作为小程序首发登录前置** |
| Cloudflare Workers / D1 / R2 候选 | 大陆可用且满足法律评估的服务商优先 | S1～S3 Worker 只保留合成数据开发基线；不将海外环境默认用于真实健康信息 |
| 演示 A/B 账号 | 只用于本地自动化测试 | 必须隔离于正式小程序及默认发布构建，绝不作为真实用户登录 |
| 页面及功能清单 | 业务能力继续沿用 | 按微信小程序 UX/路由/组件重新实现，保持事件/症状/实际执行边界 |

## 3. 推荐微信登录业务时序（未启用真实登录）

\`\`\`mermaid
sequenceDiagram
  participant M as 微信小程序
  participant A as Health API（境内待建）
  participant W as 微信 code2Session
  participant D as 用户/身份与会话库
  M->>M: wx.login() 获取一次性 code
  M->>A: POST /api/v1/auth/wechat-mini/session {code}
  A->>W: 服务器使用 AppID + AppSecret 调用 code2Session
  W-->>A: openid / session_key / optional unionid
  A->>D: 按 appid + openid 查找或受控建立身份
  A->>D: 创建可撤销、短有效期 Health 自有会话
  A-->>M: 仅返回 Health 会话凭据/最少状态
  M->>A: 带 Health 会话调用健康事件 API
  A->>D: 会话核验 + 用户归属 + 单独同意状态
  A-->>M: 只返回当前用户获授权的数据
\`\`\`

原则：

1. \`code\` 有效期短、只能使用一次；绝不在数据库中作为长期身份凭据，不应记录在 URL/日志中。
2. \`AppSecret\` 必须只保存在服务端 Secret/KMS；\`session_key\` 不能下发小程序，不能作为 Health API 的 Bearer token。
3. \`openid\` 在当前小程序 AppID 范围识别身份；如未来涉及公众号/多应用再单独评估 \`unionid\`，首发不依赖它，也不能用微信昵称作为唯一用户 ID。
4. 后端映射到自己的不可预测内部 \`user_id\`，并验证每个 \`event_id\` 的归属；用户授权和敏感健康信息同意必须独立判断。
5. 首次微信身份识别与用户同意保存真实健康信息是**不同流程**；没有单独同意前不得把真实医疗健康记录写进存储。
6. 小程序侧**不保存 session_key / appSecret / 原始病历到本地缓存**；健康 API 凭据采取最短必要有效期、退出/过期清理及可撤销策略；正式会话形式由后续实现评审定稿。
7. \`wx.getPhoneNumber\` 等手机权限**不作为首发基本录入前置条件**；如需额外获取需目的说明、必要性验证及用户单独操作。

## 4. 小程序与中国大陆部署要求

**小程序：** 需要小程序主体、AppID、类目和资质评估，以及小程序备案；具体类目取决于实际服务内容（个人信息记录 vs 在线诊疗/医药服务等不能混淆），最终按微信平台审核结果和适用法规执行。

**API 域名：** 需 HTTPS、合法 request/upload/download 域名配置和适用的域名/网站 ICP 备案要求；小程序不得直接调用微信 \`api.weixin.qq.com\` 的敏感服务端接口；服务端独立调用。

**健康信息：** 《个人信息保护法》将医疗健康列为敏感个人信息，处理需要特定目的、充分必要和适用的单独同意、必要性/权益影响告知。小程序平台隐私保护指引授权与本产品的法律告知/单独同意分别落实。

**数据所在地：** 首发**优先中国大陆境内存储与处理**，以减小访问延迟、跨境链路和合规复杂性；不等于断言中国法律规定所有健康数据无条件禁止出境。云商、可用区、日志/备份/AI/OCR 处理方均需核查具体数据流。

**医学边界：** 本期仅用户自述/记录/事实整理，不提供诊断结论、处方建议、风险分诊。未来涉及医药医疗服务或医疗器械软件时再进行类目/许可/监管判断，不提前假定已经获得资质。

## 5. 研发阶段拆分（防止需求扩散）

- **S4：客户端形态基线。** 建立微信原生小程序只读虚构数据骨架、微信登录后端适配契约与模拟测试、保留默认 fail-closed 构建。不接 AppID、真实微信账号、真实病历。
- **S5：真实微信身份和服务端会话。** 前提：小程序主体/AppID、符合要求的境内后端、API 域名、会话/数据保护设计和审核。
- **S6：首条生产级健康事件/症状链路。** 前提：正式身份、敏感信息同意、数据库安全、加密/KMS、导出/删除等通过安全阶段门。
- 后续：药物/医嘱/就医报告依照既有 PRD 优先级逐步进入研发，AI/OCR 单独审核；不因客户端调整而重开已锁定业务需求。

## 6. 仍待决定（严格最小集合）

- **小程序注册主体及 AppID：** 企业/组织/个人等实际主体，以及可使用的正式 AppID；目前仓库不得提交 AppSecret。
- **境内后端部署商及 API 域名：** 方案可以比选，但不默认选择某家；应一并核验备案、日志、备份、KMS 和服务协议。
- **手机号是否必要：** 默认不强制。只有出现明确的账号找回/联络/业务需求才进入选型，不阻断 S4。
- **真实用户年龄范围：** 建议先限成年人本人使用；未成年人和家庭代管需另行权限/监护方案，不纳入当前 MVP。
